# AtmosSense Caching Strategy

Caching is a critical component in AtmosSense to ensure low latency, high throughput, and protection against external API rate limits. We employ a multi-layered caching strategy.

## 1. Application-Level Caching (Redis)

Redis serves as our primary application cache. It is used to store frequently requested regional forecasts and rate-limiting counters.

### What is Cached?
* **Regional ML Forecasts**: The results of our ML inference engine for specific coordinates or regions.
* **External API Responses**: Raw data fetched from external weather providers.

### Cache Invalidation and TTL Strategy
Weather data is inherently time-sensitive but relatively stable over short periods. We use a **Time-To-Live (TTL)** based invalidation strategy:
* **Short TTL (10-15 minutes)**: Applied to current weather conditions and immediate external API responses to ensure data freshness.
* **Medium TTL (1-2 hours)**: Applied to ML-generated forecast trends. The ML models predict trends that are valid for several hours, so re-computing them every minute is wasteful.
* **Manual/Event-Driven Invalidation**: If the ML model is updated or if a severe weather alert is triggered, specific region cache keys can be actively invalidated.

### Cache Key Design
Keys are structured hierarchically: `atmossense:forecast:{region_code}:{timestamp_bucket}`

## 2. Edge / CDN-Style Caching (Nginx)

To reduce load on the Django application servers, we implement edge caching at the reverse proxy layer (Nginx).

### What is Cached?
* **Static Assets**: JavaScript, CSS, and images.
* **Pre-computed Forecast Tiles/JSON**: Public, non-user-specific forecast data.

### Strategy
We use HTTP `Cache-Control` headers (e.g., `Cache-Control: public, max-age=300`) generated by Django. Nginx is configured to respect these headers and cache the responses. If a client requests a forecast tile that Nginx has cached, Nginx serves it directly without ever proxying the request to Django, functioning as a simulated CDN.
